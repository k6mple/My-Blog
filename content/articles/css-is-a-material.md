三年前我接手过一个文档站。设计稿很漂亮，间距精确，节奏舒展。打开代码后，我看到十四个按钮类名、七个不同来源的圆角，以及三百多行以 `!important` 结尾的覆盖规则。页面上线后，每个新需求都会让这套规则再厚一层。

问题不在于团队不重视 CSS，而在于我们把 CSS 当成了设计完成后的最后一道工序。设计被画在画板上，CSS 只负责把它“调出来”。这种关系一旦建立，实现就注定是一场和浏览器的拉锯。

## 从「最后再调」开始

补丁式 CSS 通常有一个明显的起点：布局先靠绝对定位和固定宽度完成，颜色和边距最后再“美化”。

这样写出来的页面，在某个固定宽度下可能和设计稿一模一样，但它没有表达能力。屏幕窄一点，文字会溢出；内容多一行，卡片高度会失衡；系统字体变了，整个标题会换行。每一次修改都在修补上一次的假设。

把 CSS 当材料，意味着在开始写之前先问：这个界面想让内容以什么方式流动？

## 让布局表达约束

设计稿给出的经常是坐标，而不是意图。一个卡片在 1440px 下宽 320px、距离侧栏 64px，这些数字背后真正的约束可能是：“正文占主要空间，旁注在大屏上放在右侧，窄屏时移到下方。”

[CSS Grid](https://developer.mozilla.org/zh-CN/docs/Web/CSS/CSS_grid_layout) 最适合表达这种关系：

```css
.reader {
  display: grid;
  grid-template-columns: minmax(0, 1fr) minmax(12rem, 18rem);
  gap: clamp(2rem, 5vw, 5rem);
  align-items: start;
}

@container article (width < 48rem) {
  .reader {
    grid-template-columns: minmax(0, 1fr);
  }
}
```

这里的 `minmax(0, 1fr)` 不只是语法细节。默认情况下，网格项的最小宽度由内容决定，一段无法换行的代码或一条长链接会把整列撑破。把最小值设为 `0`，才是真正把控制权交给网格。

容器查询则把“屏幕多宽”换成了“这个组件有多少空间”。同一个文章卡片放在首页主栏和侧边栏时，应该根据自身容器决定排版，而不是猜测视口宽度。

### 流，而不是坐标

我越来越少给组件写固定高度。不是绝对不能用，而是固定高度会把内容当成已知常量，而内容恰恰是最不稳定的部分。

一个中文标题的换行位置可能随字体、字距和断行规则变化；一段说明可能因为翻译长出两行；一个按钮的文案可能在上线前被替换。好的布局应该能吸收这些变化，而不是要求内容永远保持原样。

这也是为什么我更愿意用：

```css
.section {
  display: flex;
  flex-direction: column;
  gap: clamp(2rem, 5vw, 4.5rem);
  padding-block: clamp(4rem, 10vw, 8rem);
}
```

而不是给每个子元素单独设置 `margin-top`。前者描述的是一个区间内的节奏，后者描述的是一组脆弱的坐标。

## 层叠是一份协议

很多 CSS 混乱，不是因为选择器不会写，而是因为层叠缺少秩序。谁覆盖谁，变成了一件需要靠记忆和猜测解决的事。

`@layer` 让层叠顺序成为一份显式协议：

```css
@layer reset, tokens, base, layout, components, utilities;

@layer tokens {
  :root {
    --surface-raised: #141416;
    --text-primary: #f5f5f7;
    --line-subtle: rgb(255 255 255 / 0.09);
  }
}

@layer components {
  .card {
    background: var(--surface-raised);
    border: 1px solid var(--line-subtle);
  }
}
```

声明顺序在文件顶部，覆盖关系就不再取决于选择器权重，也不需要 `!important` 来救场。工具类和组件层可以各自演进，边界清楚。

不过，层叠顺序不是越多越好。五到六个层足够大多数项目使用。把每一个组件都放进独立层级，最后只会得到另一套需要记忆的目录。

## 组件负责结构，不负责位置

我经常看到组件自带 `margin: 24px`，于是父级为了修正间距，又要加一层负边距或额外的包装元素。

组件的职责是把自身内部组织好；它应该被放置在哪里，是父级布局的职责。让父级用 `gap` 管理一组卡片之间的关系，组件就获得了一个干净的边界：

```css
.card-grid {
  display: grid;
  grid-template-columns: repeat(auto-fit, minmax(min(100%, 18rem), 1fr));
  gap: 1rem;
}
```

这段代码不需要媒体查询，就能在窄屏自动变成单列，在有空间时扩展为多列。它同时处理了容器比 18rem 还窄的边界情况，而不需要某个特定断点来救场。

这不是“用现代 CSS 取代媒体查询”的教条。媒体查询依然适合表达内容结构的变化，例如导航从横向变成抽屉。但纯粹由空间驱动的重排，交给流式布局会更稳。

## 设计系统要留下余地

设计系统的目标是降低重复决策，而不是消灭判断。

我不再为每一个值都创建 token。一个只被使用一次、也没有语义价值的数值，直接写在组件里并不可耻。真正值得被命名的，是那些跨页面共享的决定：表面层级、正文颜色、焦点样式、页面节奏。

同样重要的是，让 token 描述角色，而不是外观。`--color-blue-500` 在暗色主题里会变得尴尬，`--color-accent` 则能继续成立。焦点环、错误色和选中色也应该有各自的语义，而不是在业务代码里临时挑一个色值。

## 材料的手感来自一致性

材质不是叠一层磨砂玻璃，也不是到处加渐变。它更像一束光照过不同表面时，明暗关系是否连续。

如果导航栏是半透明加模糊，正文卡片就应该有相近的边框亮度和阴影深度；如果强调色只在关键动作出现，它就不该同时被用在装饰性标签上。一致性不是重复同一个圆角，而是回答同一类问题时不反复改口。

CSS 是唯一同时接触排版、色彩、空间和交互的技术。正因为它离视觉太近，我们更容易把它当作审美的附属品。但它其实是界面的物理法则。法则越清楚，设计越自由。

> CSS 不是设计完成后的实现细节。它决定了设计在真实内容、真实设备和真实用户面前，能否站得住。

## 在实现中继续设计

现在接到一个新页面，我会先写三件事：内容的流动路径、允许的宽度范围、错误和空状态。写完这些，才开始调整颜色。

这听起来像是把设计往后推，实际上是把设计往前拉。只有当结构能够容纳变化，视觉才有机会显得从容。

补丁只能解决这一屏。材料才能决定这座房子能住多久。
