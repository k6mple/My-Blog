React Server Components 改变的并不是“组件在哪里渲染”，而是我们如何给一个界面划分职责。

刚接触 RSC 时，我犯过一个典型错误：把它当成分包工具。凡是页面里不涉及点击的部分，全部改成服务端组件；需要点击的地方，再单独标记 `"use client"`。代码看起来更“新”，但数据流和职责边界变得比原来更难解释。

后来我给自己换了一个问题：这个组件理解的是数据，还是人的意图？

## 交互不是唯一的判断标准

“有 `onClick` 就是客户端组件”是必要不充分条件。

一个服务端组件可以读取数据库、决定页面结构、处理权限，但它不负责响应。一个客户端组件可以承载焦点、乐观更新和过渡状态，也可以只是把服务端送来的数据包进一段交互里。

真正的边界通常出现在这几种地方：

- 数据从可信环境进入浏览器的那一刻；
- 用户输入改变界面局部状态的那一刻；
- 第三方库需要在浏览器生命周期里运行的那一刻；
- 一段组件需要被单独缓存、复用或延迟加载的那一刻。

如果边界不清晰，最先出现的不是性能问题，而是理解成本。

## 把数据留在离数据近的地方

一个文章页需要当前文章、相关文章和读者的书签状态。前两者适合在服务端读取，书签按钮则只关心“是否已收藏”和一次网络请求。

我倾向于这样组织：

```tsx
// app/posts/[slug]/page.tsx
export default async function PostPage({ params }: Props) {
  const { slug } = await params;
  const post = await getPost(slug);

  return (
    <Article>
      <ArticleBody content={post.content} />
      <BookmarkButton postId={post.id} />
      <RelatedPosts posts={post.related} />
    </Article>
  );
}
```

文章主体不需要进入客户端 bundle，相关文章可以在服务端直接展开，而 `BookmarkButton` 只需要拿到一个稳定的 `postId`。数据在离它近的一侧被读取，交互在需要它的地方发生。

这听起来很朴素，但它避免了一个常见的反模式：把整个页面做成客户端组件，再从一个很宽的接口里取回所有数据，其中包括大量只用于初始渲染的字段。

## 序列化是设计约束

服务端与客户端之间传递的 props 必须可序列化。这个限制看似麻烦，实际上很有用：它会提醒你，什么应该跨过边界。

我尽量只传已经处理过的、稳定的数据：字符串、数字、简单对象、已经序列化的内容。不要把数据库连接、类实例或一个包含大量方法的对象带到客户端。

如果某个组件需要的数据形状很复杂，通常意味着两个问题之一：服务端还没有把它整理好，或者客户端承担了过多它不需要理解的业务逻辑。

## 客户端岛屿要小，但要完整

一个常见误区是把客户端组件切得越碎越好。结果是一个交互被拆到三个组件里，状态通过 props 一路传递，焦点和错误处理反而没有归属。

我宁愿让一个客户端组件完整地拥有一段交互：输入框、结果列表、空状态、错误提示、键盘行为都放在一起。它的边界应该围住一个完整的人的任务，而不只是一个 DOM 节点。

```tsx
"use client";

export function SearchField({ onSearch }: Props) {
  const [query, setQuery] = useState("");
  const deferredQuery = useDeferredValue(query);

  return (
    <div className="search-field">
      <SearchInput value={query} onChange={setQuery} />
      <SearchResults query={deferredQuery} onSearch={onSearch} />
    </div>
  );
}
```

这段组件拿走的 JavaScript 是值得的：它让搜索可以即时响应，并且在用户还没按下回车时就开始工作。它不应该拿走的是整个页面的排版和静态内容。

## 一个更小的检查清单

在标记 `"use client"` 之前，我会问：

- 这段代码必须知道浏览器的存在吗？
- 它需要的数据是否可以由父级在服务端准备好？
- 它的状态变化会影响多少其他组件？
- 如果 JavaScript 加载失败，它是否还有可以理解的静态表达？

最后一个问题尤其重要。渐进增强不是旧时代的遗物，而是界面对失败保持体面的一种能力。

## 边界感

RSC 最有价值的地方，不是减少了多少字节，而是迫使我们重新讨论组件的职责。

一个好的边界，应该让服务端负责确定性和数据，让客户端负责人的动作和即时反馈。两侧都不越权，组件才真正可读。

> 性能通常是边界清晰的副产品，而不是目标本身。
